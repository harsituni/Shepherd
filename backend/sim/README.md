# Wildfire sim

The live hazard behind `/sim/*`, `/hazards` and `/forecast`, and the frozen
forecast that routing reads. The wildfire is the supported hazard; the tornado
is a **beta** feature. Both are prototype models, not operational predictions.

## Files

| File | What it does |
|---|---|
| `controller.py` | `SimController`, the API's single sim: start / pause / resume / reset / speed / wind, ticked every 2 s |
| `tornado.py` | `TornadoSim` (**beta**): same surface as `WildfireSim`, plus EF stats for `/sim/state` |
| `wildfire.py` | `WildfireSim`: one fire on the engine, with `step`, `features` (the fire now), `forecast` (+15…+120 outlines), `set_wind` and `oracle` |
| `oracle.py` | `ForecastOracle`, the read-only arrival grid snapshot routing uses, and `validation_error()` |
| `engine/` | The spread model: `run_simulation(scenario) -> SimulationResult` |
| `weatherpipe/` | Live OpenWeather forecast → the hourly wind series the fire runs on |
| `tests/` | Engine, weather and sim tests (offline; provider calls are mocked) |
| `weather_cache/` | Forecasts fetched from OpenWeather (git-ignored) |

## How a fire runs

`/sim/start` builds a `WildfireSim` at the clicked point. The fire starts as a
300 m circle on a 100 m grid that covers a 10 × 10 km square around it, widened
to the road graph's box (the API passes it) so routing has a forecast
everywhere it routes. `fuel_dryness` (or `humidity_pct`, which overrides it)
sets the fine fuel moisture code.

The engine always computes the whole fire from minute 0. The sim keeps one
finished result reaching at least 240 minutes past now (plus 240 of lookahead,
so reruns are rare) and swaps in a new one when it needs to see further or the
wind changes. A run takes tens of milliseconds on the 10 km square and
0.1–0.2 s across the city. Reads never wait for a run. `set_wind()` keeps the
weather up to now and applies the new wind from the next minute, so nothing
that has burned changes.

`oracle()` returns a frozen `ForecastOracle` (arrival minute per cell, `+inf`
where the fire doesn't reach by the horizon, and the domain mask). The same
object comes back until the sim moves or reruns, so a paused sim hands out one
snapshot; `version` changes on every rerun.

## Weather

`SimController(weather="forecast")` (the default) asks `weatherpipe.live` for
the fire's location, in this order: a fetch for the same 0.01° cell in the last
10 minutes, a live OpenWeather 3-hourly forecast (4 s timeout, no retries), then
the newest cached forecast within 25 km. If none works, the fire uses the wind
sent with `/sim/start`, held constant. `weather="dashboard"` always uses the
sent wind. `/sim/wind` overrides either from that minute on.

Set `OPENWEATHER_API_KEY` in the repo-root `.env` (see `.env.example`). Wind
leaves the pipeline as OpenWeather reports it: m/s, direction it blows FROM.
Only the engine converts to km/h and to a spread bearing.

## The engine

Model assumptions (none of them a conservative bound on real fire spread):
Canadian FBP System, uniform M-1/M-2 fuel with a fixed conifer share, FFMC and
BUI; temperature, humidity and rain don't change moisture; flat ground and
instantaneous equilibrium spread; every domain cell burnable (no barriers,
suppression or spotting); one uniform wind for the whole domain, interpolated as
vectors over time, bearings on UTM 12N grid north.

Spread is a time-dependent Dijkstra over a 16-direction stencil: directional
rates are evaluated at time knots (every `integration_step_min`, plus each
forecast time), integrated into cumulative distance per direction, and each
crossing arrives at the earliest time that distance is covered. Because rates
are never negative an earlier start never arrives later, which is what lets
Dijkstra settle each cell once. One arrival time stands for the whole cell.

Scenario input (`engine/contracts.py`, validated with pydantic): `t0`,
`horizon_min`, `bbox` (lon/lat, UTM zone 12N only, at most 2 million cells), an
`ignition` point or `initial_perimeter` polygon, `cell_m`,
`integration_step_min`, an hourly `weather` series from `t_min` 0, a
`weather_end_policy` (`error` or `hold`) and `fbp` parameters. The result is an
immutable `(rows, cols)` float32 grid of arrival minutes (NaN = not reached),
row 0 at the north edge.

The domain edge is a lon/lat rectangle; it is densified before projecting to
UTM so curved edges keep their boundary cells, and the domain mask counts a
cell when its closed square touches the domain.

Checks behind the numbers: FBP rates match an independent 50-digit Decimal
calculation of the published equations (`tests/fixtures/fbp_reference.json`,
regenerated by `generate_fbp_reference.py`), and a wind reversal mid-crossing
matches an independent midpoint reference to 0.0004 min at the default step.

## Tornado (beta)

`/sim/start` with `"scenario": "tornado"` runs `TornadoSim`. Beta: it runs end
to end (map, forecast, routing, traffic), but the model is a simple demo and
may change. It doesn't use the FBP engine or live weather: the storm travels
with the dashboard's wind (direction FROM + 180°, speed a fraction of the wind)
and meanders on the right-rear flank of the storm. Peak strength is an EF0–EF5
rating (`ef_rating`, else picked from the wind) with a life cycle (organizing,
mature, dissipating), which sets the core radius and damage-path width.
`features()` gives the core, the debris wrap and the damage scar; `forecast()`
the core at +15…+120; `oracle()` paints the arrival minute along the predicted
track on a 100 m grid, so routing judges roads exactly as it does for a fire.
